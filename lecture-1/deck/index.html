Five suspicious situations

Where does malware stop?

Five situations, ordered by distance from the file. Which of them is malware?

PowerShell downloads and runs code — a command, and whatever it fetches.

Start with the left column. It is the first two periods on slides 10 and 11: the executable era proper, and then the period in which the file diversified into documents, scripts and exploit objects but remained the deliverable. For roughly fifteen years the attacker's problem was to get their own code onto the victim's machine and run it, because the victim's machine offered little else to work with. PowerShell did not ship by default until Windows 7 in 2009, remote-management tooling was not ubiquitous, and business data lived on the host rather than behind cloud APIs. Files cross the boundary the defender controls, persist long enough to inspect, hash identically everywhere, and can be scanned before they run. Read the five tracks as one system, starting with the money. The attacker's unit was the executable because the victim ran as administrator on a machine with no built-in tooling worth abusing, received email and browsed with plug-in-heavy browsers, and the network carried everything in the clear. The defenses that mattered were exactly those built on that unit: file scanners, payload signatures, spam filters.

Motive explains the volume. The decade opens with worm authors seeking notoriety and closes with a criminal market. Adware and pay-per-install paid per infected machine; spam botnets rented out capacity; the same botnets sold DDoS, first as extortion of online businesses and then as a service for hire (Ancheta, indicted in November 2005 for selling botnet access for DDoS and spam, was the first US prosecution of its kind); click fraud monetized browsers; banking trojans and carding monetized credentials. Once an infection was worth a few cents to a few dollars, the attacker's problem became scale, and scale is what produced botnets and server-side polymorphism. The product was the victim's machine, its bandwidth and what it typed.

Worms, then botnets. The first half of the decade belongs to the worms: Code Red and Nimda in 2001, Slammer and Blaster in 2003, Sasser in 2004, each exploiting an unpatched service on a machine with no firewall and spreading with no user action. XP SP2 turning the firewall on in August 2004 is the defender's answer, and the big network worms go quiet until Conficker finds MS08-067 in 2008. The second half belongs to the botnets. The IRC bot families (Agobot, SDBot, rxbot) made the compromised machine report to a channel and take orders, which is what turned infections into inventory that could be rented for spam, DDoS and installs; Ancheta was prosecuted for exactly that trade. Storm, Zeus, Conficker and Koobface are the mature form: the machine is the product and the binary is disposable.

Each block got an answer. Outlook blocked executable attachments in 2000 and Gmail from 2004, zips included; the mass-mailers switched to zip within weeks (MyDoom, January 2004) and to password-protected zips with the password shown as an image (Bagle, February to March 2004). When the IM worms of 2005 made MSN Messenger filter .pif and executable transfers, Kelvir was already sending a link instead. Exploit documents (a Word zero-day in May 2006, PDF in November 2008) and MPack, the first exploit kit sold commercially (2007), are the same answer with a different container: the file diversified as soon as the executable was blocked, which is why slide 14's first bar starts in this period and not in 2010.

Within the decade the attacker moved three times inside the file:

  • Packers and protectors made the bytes on disk stop matching the code that ran. Antivirus added emulation and generic unpacking: the scanner ran the file a little to see it.
  • Rootkits and bootkits made the live system lie about which files and processes existed. The Sony BMG case in 2005 made the technique public. Defenders inspected raw disk and memory from outside the lying layer, and Microsoft's 64-bit kernel-patch protection (2005) and Vista's mandatory driver signing (2007) were in part a response.
  • Botnets and server-side polymorphism turned the host into a rented commodity and gave every victim a unique binary. The asset was the command-and-control infrastructure; the binary was disposable. This broke hash and byte signatures operationally and produced reputation and prevalence systems (McAfee Artemis in 2008, Symantec Quorum and Insight in 2009–2010), cloud lookups, generic detections, and pushed machine learning on file features from research (first papers in 2001) toward products (from about 2012). Lecture 3 picks that up.

The operating-system row explains why so much was possible: administrator by default, autorun, and no exploit mitigations until SP2 and Vista. Vista's UAC and driver signing were unpopular precisely because they took privileges away from the model attackers had been enjoying.

Default story, three events and one image. Windows XP (2001): everyone an administrator, autorun on, firewall off. The IRC botnets of 2003–2004 and the Ancheta case: the infected machine becomes inventory, sold for spam, DDoS and installs. Storm (2007) and McAfee Artemis (2008): a unique binary per victim, answered by reputation in the cloud. The image for students who were not there: in August 2003 an unpatched XP laptop plugged into a university network was infected by Blaster within minutes, with nothing opened and nothing clicked.

Read the five tracks as one system, starting with the money. The attacker's unit was the executable because the victim ran as administrator on a machine with no built-in tooling worth abusing, received email and browsed with plug-in-heavy browsers, and the network carried everything in the clear. The defenses that mattered were exactly those built on that unit: file scanners, payload signatures, spam filters.

Motive explains the volume. The decade opens with worm authors seeking notoriety and closes with a criminal market. Adware and pay-per-install paid per infected machine; spam botnets rented out capacity; the same botnets sold DDoS, first as extortion of online businesses and then as a service for hire (Ancheta, indicted in November 2005 for selling botnet access for DDoS and spam, was the first US prosecution of its kind); click fraud monetized browsers; banking trojans and carding monetized credentials. Once an infection was worth a few cents to a few dollars, the attacker's problem became scale, and scale is what produced botnets and server-side polymorphism. The product was the victim's machine, its bandwidth and what it typed.

Worms, then botnets. The first half of the decade belongs to the worms: Code Red and Nimda in 2001, Slammer and Blaster in 2003, Sasser in 2004, each exploiting an unpatched service on a machine with no firewall and spreading with no user action. XP SP2 turning the firewall on in August 2004 is the defender's answer, and the big network worms go quiet until Conficker finds MS08-067 in 2008. The second half belongs to the botnets. The IRC bot families (Agobot, SDBot, rxbot) made the compromised machine report to a channel and take orders, which is what turned infections into inventory that could be rented for spam, DDoS and installs; Ancheta was prosecuted for exactly that trade. Storm, Zeus, Conficker and Koobface are the mature form: the machine is the product and the binary is disposable.

Each block got an answer. Outlook blocked executable attachments in 2000 and Gmail from 2004, zips included; the mass-mailers switched to zip within weeks (MyDoom, January 2004) and to password-protected zips with the password shown as an image (Bagle, February to March 2004). When the IM worms of 2005 made MSN Messenger filter .pif and executable transfers, Kelvir was already sending a link instead. Exploit documents (a Word zero-day in May 2006, PDF in November 2008) and MPack, the first exploit kit sold commercially (2007), are the same answer with a different container: the file diversified as soon as the executable was blocked, which is why slide 14's first bar starts in this period and not in 2010.

Within the decade the attacker moved three times inside the file:

  • Packers and protectors made the bytes on disk stop matching the code that ran. Antivirus added emulation and generic unpacking: the scanner ran the file a little to see it.
  • Rootkits and bootkits made the live system lie about which files and processes existed. The Sony BMG case in 2005 made the technique public. Defenders inspected raw disk and memory from outside the lying layer, and Microsoft's 64-bit kernel-patch protection (2005) and Vista's mandatory driver signing (2007) were in part a response.
  • Botnets and server-side polymorphism turned the host into a rented commodity and gave every victim a unique binary. The asset was the command-and-control infrastructure; the binary was disposable. This broke hash and byte signatures operationally and produced reputation and prevalence systems (McAfee Artemis in 2008, Symantec Quorum and Insight in 2009–2010), cloud lookups, generic detections, and pushed machine learning on file features from research (first papers in 2001) toward products (from about 2012). Lecture 3 picks that up.

The operating-system row explains why so much was possible: administrator by default, autorun, and no exploit mitigations until SP2 and Vista. Vista's UAC and driver signing were unpopular precisely because they took privileges away from the model attackers had been enjoying.

The Snowden disclosures from June 2013 turned HTTPS from a login-page feature into the default: the IETF declared pervasive monitoring an attack, Let's Encrypt made certificates free, and half of page loads were encrypted by late 2016. Each row is something students have just seen, now stated as a break in the model from slide 6, ordered by when it became dominant rather than when it was first seen. Every row has a precedent, and the first row is the clearest case of defense causing the next move. Macro viruses from 1995 and the VBScript worms of 2000–2001 were the first wave of non-executable files; Office macro security levels and Outlook attachment blocking absorbed them. Then the channels blocked the executable itself, and the dates matter because they are earlier than students expect: Outlook in June 2000 and by default from Outlook 2002, Gmail from its first months in 2004 with zip archives included, the mail gateways in between, MSN Messenger in April 2005 after the Bropia and Kelvir worms, Facebook Messages from their launch in November 2010. Each block was answered within months, and the answer was always a container the block did not cover. MyDoom mailed itself in zip archives in January 2004 and Bagle in password-protected zips a month later, with the password shown as an image by March. Kelvir sent a link to its .pif rather than the file, which the messenger filter did not catch, and Koobface spread through social networks by link from 2008. A Word zero-day carried targeted attacks in May 2006, a PDF exploit with zero antivirus detections circulated in November 2008, and MPack, the first exploit kit sold commercially, was documented in 2007; from then on the browser, not the attachment, delivered the executable. Macro documents returned in 2014, and JavaScript, VBScript and HTA downloaders, shortcut files and ISO images followed each later block. The collaboration tools of the 2020s repeat the cycle: Teams carried Storm-0324's phishing in 2023 and Black Basta's fake help-desk calls in 2024, and Discord's content network hosted payloads until it switched to expiring links in November 2023. That diversification is what changed what the sandbox had to detonate, and it is why the first bar on the timeline starts in 2004 rather than 2010: dominance came later, the diversification began the moment the executable was blocked. The row now also carries the diversification inside the executable: from about 2020 implants, loaders and ransomware moved to Go, Rust and .NET (BlackCat in Rust in November 2021 is the marker), all still PE files, but each runtime needs its own unpacking, symbol recovery and decompilation, so this break is at extraction as much as at the sensor; Part 2's options slide has the row for it. Memory-resident code and living off the land likewise have earlier precedents; what matters for the defender is the moment a technique stops being an exception and becomes the default.

Make the causal point explicit now that the evidence is on the table. File-centric defense worked: signatures, reputation, cloud lookups, download warnings and code-signing enforcement made delivering an unknown executable expensive, so attackers diversified the file. Sandboxes made the unknown document and dropped executable expensive, so attackers went to memory and built-in tools. EDR made implants visible, so attackers went to identities, vendors and remote-management tools. Operating-system hardening closed the host, so attackers went to people, edge devices and agents. Each row is partly a consequence of winning the previous row.

The second callout is the motive track read across the four periods. Defensive success explains why the attacker had to move; the payout explains where they moved to. When the product was the machine, the attack was a file on the machine. When the product became the organization's willingness to pay, the attack became access to the organization. When the product became identity and data in SaaS, the attack became a token or an instruction. Students who remember only this sentence can reconstruct most of the table.

What did not change. The person as the way in, and the file as a carrier. Phishing is the one initial-access capability that runs unchanged from the executable attachments of 2000 to the help-desk calls and ClickFix lures of 2024; the tracks do not show it because it never moved, and that is why it survives every row of this table. And the file never left: most campaigns still begin with an executable or a document, and the implants, loaders and infostealers sold on criminal markets in 2026 are files, now in Go, Rust and .NET, some with an LLM call inside (slide 13). This table records that the file stopped being required, not that it became rare; a lecture that says "malware is no longer a file" has overstated its own evidence.

In the words of the four questions that close Part 1 (slide 18): the artifact carried the malicious meaning in the file era; the APT era added objective, because the same file meant something different inside a campaign; the access economy moved the meaning to control, since a legitimate tool, a valid token or a real vendor update was malicious only because of who held it; and the agent period adds a controller that is itself a program acting under delegated authority, so control and objective have to be read from the agent's context and actions. Each move is also a move in what evidence the defender needs, which is the second half of the lecture.

Avoid claiming that “fileless” always means literally no disk artifacts. The important distinction is that the primary malicious capability may never appear as a conventional executable file supplied to a scanner. The first row is the mildest break: still a file, no longer an executable, which is why file-based defenses extended rather than collapsed in that period.

Cloud and identity abuse go further: the attacker may realize an objective through legitimate APIs without delivering executable code to the victim host. The last row goes further still: the thing that executes is an instruction consumed by a program that was supposed to be on the defender's side.

Each row is something students have just seen, now stated as a break in the model from slide 6, ordered by when it became dominant rather than when it was first seen. Every row has a precedent, and the first row is the clearest case of defense causing the next move. Macro viruses from 1995 and the VBScript worms of 2000–2001 were the first wave of non-executable files; Office macro security levels and Outlook attachment blocking absorbed them. Then the channels blocked the executable itself, and the dates matter because they are earlier than students expect: Outlook in June 2000 and by default from Outlook 2002, Gmail from its first months in 2004 with zip archives included, the mail gateways in between, MSN Messenger in April 2005 after the Bropia and Kelvir worms, Facebook Messages from their launch in November 2010. MyDoom mailed itself in zip archives in January 2004 and Bagle in password-protected zips a month later, with the password shown as an image by March. Kelvir sent a link to its .pif rather than the file, which the messenger filter did not catch, and Koobface spread through social networks by link from 2008. A Word zero-day carried targeted attacks in May 2006, a PDF exploit with zero antivirus detections circulated in November 2008, and MPack, the first exploit kit sold commercially, was documented in 2007; from then on the browser, not the attachment, delivered the executable. Macro documents returned in 2014, and JavaScript, VBScript and HTA downloaders, shortcut files and ISO images followed each later block. That diversification is what changed what the sandbox had to detonate, and it is why the first bar on the timeline starts in 2004 rather than 2010: dominance came later, the diversification began the moment the executable was blocked. The row now also carries the diversification inside the executable: from about 2020 implants, loaders and ransomware moved to Go, Rust and .NET (BlackCat in Rust in November 2021 is the marker), all still PE files, but each runtime needs its own unpacking, symbol recovery and decompilation, so this break is at extraction as much as at the sensor; Part 2's options slide has the row for it. Memory-resident code and living off the land likewise have earlier precedents; what matters for the defender is the moment a technique stops being an exception and becomes the default.

Make the causal point explicit now that the evidence is on the table. File-centric defense worked: signatures, reputation, cloud lookups, download warnings and code-signing enforcement made delivering an unknown executable expensive, so attackers diversified the file. Sandboxes made the unknown document and dropped executable expensive, so attackers went to memory and built-in tools. EDR made implants visible, so attackers went to identities, vendors and remote-management tools. Operating-system hardening closed the host, so attackers went to people, edge devices and agents. Each row is partly a consequence of winning the previous row.

The second callout is the motive track read across the four periods. Defensive success explains why the attacker had to move; the payout explains where they moved to. When the product was the machine, the attack was a file on the machine. When the product became the organization's willingness to pay, the attack became access to the organization. When the product became identity and data in SaaS, the attack became a token or an instruction. Students who remember only this sentence can reconstruct most of the table.

The figure is the one measurement in Part 1 that states the thesis as a number: the share of CrowdStrike's detections that involved no malware file went from 40 percent in 2018 to 79 percent in 2024 (the 2021 point is the fourth quarter of that year). Say that the metric is one vendor's telemetry and that the direction, not the decimal, is the point.

What did not change. The person as the way in, and the file as a carrier. Phishing is the one initial-access capability that runs unchanged from the executable attachments of 2000 to the help-desk calls and ClickFix lures of 2024; the tracks do not show it because it never moved, and that is why it survives every row of this table. And the file never left: most campaigns still begin with an executable or a document, and the implants, loaders and infostealers sold on criminal markets in 2026 are files, now in Go, Rust and .NET, some with an LLM call inside (slide 13). This table records that the file stopped being required, not that it became rare; a lecture that says "malware is no longer a file" has overstated its own evidence.

In the words of the four questions that close Part 1 (slide 18): the artifact carried the malicious meaning in the file era; the APT era added objective, because the same file meant something different inside a campaign; the access economy moved the meaning to control, since a legitimate tool, a valid token or a real vendor update was malicious only because of who held it; and the agent period adds a controller that is itself a program acting under delegated authority, so control and objective have to be read from the agent's context and actions. Each move is also a move in what evidence the defender needs, which is the second half of the lecture.

Avoid claiming that “fileless” always means literally no disk artifacts. The important distinction is that the primary malicious capability may never appear as a conventional executable file supplied to a scanner. The first row is the mildest break: still a file, no longer an executable, which is why file-based defenses extended rather than collapsed in that period.

Cloud and identity abuse go further: the attacker may realize an objective through legitimate APIs without delivering executable code to the victim host. The last row goes further still: the thing that executes is an instruction consumed by a program that was supposed to be on the defender's side.

Capabilities delivered through benign files

Same tool, different procedures; same technique, different tools. And when the artifact itself is legitimate and unchanged, where does “malicious” reside?

A remote-management tool abused — T1219 Remote Access Tools, an ATT&CK tool, not malware. The same binary and hash as every other install; what differs is who operates the session and whose objective it serves.

A vulnerable signed driver — T1068 Exploitation for Privilege Escalation. The same binary and hash the vendor shipped; what differs is who loads it, and that its flaw is used beyond the driver's intended design.

As files, both are identical to their legitimate copies. What makes them malicious lives outside the file: who is in control and to what end, and, for the driver, what its flaw lets them do.

The complete detection pipeline

What can a sensor see, and what has to happen before a detector sees anything?

A detector cannot reason about evidence it never receives.

Sensor — can the system observe the event or state? Where the pipeline touches reality: a hook, a tap, a log. For example file-system hooks, process and script telemetry, a network tap, identity and SaaS logs, the agent's harness.

Acquisition — is the evidence collected and retained? Seeing is not keeping: what is captured, and for how long. For example capture the file on write, triggered memory capture, packets for hours, flow records for months, central forwarding.

Extraction — can usable artifacts or fields be recovered? Raw evidence becomes something analyzable, and this stage has failures of its own. For example file parsing, unpacking and emulation, script deobfuscation, decompilation, TLS decryption, process-tree reconstruction.

Representation — what information is supplied to analysis? What a model is allowed to learn from, and what was discarded before it arrived. For example hashes and byte patterns, engineered features, sequences, graphs, text.

Detection — is a score, rule, or verdict produced? The only stage most people call detection. For example signatures, expert rules, classifiers, anomaly baselines, similarity, reputation.

Investigation — can evidence be connected and explained? Where the expensive methods live. For example enrichment, timelines across sources, detonation, forensics, reverse engineering, LLM-assisted analysis.

Decision — can an appropriate action be selected? Where authority is designed. For example automatic block above a threshold, approval playbooks, pre-authorized containment, escalation.

Response — can the action be executed in time? A detection is not an outcome until this works. For example isolate and quarantine, revoke tokens, block destinations, restore, patch, revoke an agent's tools.

Options at each stage

Every stage has options, and every line here came from that history; the sensor and extraction rows changed most.

Sensor — can the system observe the event or state?

  • File system and on-write hooks — files written, opened, executed
  • Process and script telemetry — process trees, command lines, script content (ETW, Sysmon, AMSI, script block logging)
  • Memory scanning — injected or reflectively loaded code, hooks
  • Network tap, proxy, NDR — flows, DNS, TLS metadata; payload only with decryption
  • Identity and SaaS audit logs — sign-ins, tokens, consent, data access
  • Cloud control-plane logs — API calls, role assumptions, configuration changes
  • Mail and web gateways — attachments, URLs, downloads at delivery
  • Agent harness logs — context assembled, tool calls, actions, identity used

Acquisition — is the evidence collected and retained?

  • Capture the artifact on write or on execute — the file as delivered
  • Triggered memory capture — the process or region at alert time
  • Full packet capture — everything on the wire
  • Metadata-only flow records — long, cheap retention
  • Log retention windows and sampling — what is kept, for how long
  • Central forwarding — correlation across hosts

Extraction — can usable artifacts or fields be recovered?

  • File parsing (PE, Office, PDF, archives) — structure, imports, embedded objects
  • Unpacking and emulation — code hidden behind packers
  • Script and macro deobfuscation — the command that actually runs
  • Disassembly and decompilation — functions, control flow; .NET, Go and Rust each need their own tooling
  • TLS decryption at a proxy — payload content
  • Process-tree and session reconstruction — who started what, under which identity

Representation — what information is supplied to analysis?

  • Hashes and byte patterns — exact identity
  • Engineered features — headers, imports, strings, entropy: fast, interpretable
  • Sequences (API calls, events, bytes) — order
  • Graphs — process trees, call graphs, identity graphs: relationships
  • Similarity sketches — neighbors and families
  • Text (decompiled code, logs, reports) — semantics an LLM can read

Detection — is a score, rule, or verdict produced?

  • Signatures and indicators — known threats, cheaply
  • Expert rules (YARA, Sigma, Snort) — capability patterns across hosts and traffic
  • Supervised classifiers — generalization inside the training distribution
  • Anomaly detection and baselining — deviations without a label
  • Similarity and clustering — campaign grouping, novelty
  • Reputation and prevalence — rare or new objects

Investigation — can evidence be connected and explained?

  • Triage and enrichment — context from intelligence, asset and identity data
  • Timeline reconstruction across sources — the sequence of events
  • Sandbox detonation — a captured artifact's behavior
  • Memory and disk forensics — what actually ran
  • Reverse engineering — the capability in full
  • LLM-assisted analysis — summaries, hypotheses, tool orchestration

Decision — can an appropriate action be selected?

  • Automatic block above a threshold — speed
  • Human approval playbooks — accountability
  • Risk-based policy by asset criticality — proportional response
  • Pre-authorized containment — speed with accountability, for defined scenarios
  • Escalation and deferral — expert judgment

Response — can the action be executed in time?

  • Isolate, kill, quarantine — stops host activity: isolate the host, kill the process, quarantine the file
  • Revoke tokens, reset credentials — stops identity-led activity: revoke sessions, reset credentials, disable accounts
  • Block destinations and domains — cuts the channel
  • Restore from backup, roll back changes — recovery
  • Patch and reconfigure — closes the entry
  • Revoke an agent's tools or authority — stops a hijacked agent

Two points to state while the cases are discussed. First, only some misses can be repaired by retraining the classifier; make students name the failed stage before they propose a larger model, and remember the miss that is not a miss at all, when no malicious activity occurred. Second, a detection is not an outcome: a correct alert that arrives too late, lacks recoverable evidence, or cannot trigger containment is not equivalent to stopping the attack. Cases D to F make that second point concrete.

A and C together carry the memory nuance. Once an EDR sees executable private memory or a protection change, that is observable and is not a verdict: PowerShell runs on .NET and the CLR legitimately compiles code into process memory at run time, as do browsers, JVMs and instrumentation. Visibility is not distinguishability, and distinguishability is not a verdict. The defender needs the context the representation has to keep: identity and process ancestry, command and script content, network provenance, the memory region's provenance and backing, control transfers and follow-on behavior. That is why A is a sensor failure and C a representation or classifier one: once the sensor sat on the host the problem moved down the pipeline, it did not disappear.
